# The hold-harmless set: infrastructure this feed will never block, whatever the graph says.
#
# A free blocker that a hundred strangers install is a loaded weapon pointed at the internet. The
# graph is large and mostly right; "mostly" is not good enough when the cost of a false positive is a
# stranger's site going dark, or worse, their resolver going dark and taking every name with it.
#
# SEMANTICS. An entry is an address or a prefix. A candidate prefix is REFUSED if it CONTAINS any
# entry here, and also if it is CONTAINED BY one. The first direction matters because we receive
# verdicts at whatever length a prefix is announced at, so a /20 that happens to cover K-root must be
# refused without us needing to know K-root's announced length. Refusing a candidate removes it from
# the snapshot entirely; it is not downgraded, flagged or made configurable, because an operator
# cannot be asked to know which of these addresses their resolver depends on.
#
# A refusal is counted and named in the build report, so a legitimate listing that happens to cover
# critical infrastructure is visible to us rather than silently dropped.
#
# THE STANDING RULE FOR ADDING AN ENTRY. An exemption is only safe if it is not OCCUPIABLE: an
# attacker can exploit an exemption only by hosting inside it. Root servers, public resolvers,
# registry service prefixes, NTP and CA infrastructure and reserved space are all unoccupiable at the
# lengths used here. Anything an attacker could rent space inside - cloud, CDN, general hosting, or
# anything wider than a /24 of non-registry space - is NOT an acceptable exemption, which is why the
# registry entries below are per-service /24s and /48s and never the covering supernet.
#
# THE ONE CARVE-OUT, stated because the rule above forbids it on its face. A prefix wider than a /24
# is acceptable when the ENTIRE prefix is a single operator's own infrastructure allocation with
# nothing rentable inside it, because then there is no space for an attacker to occupy at any length.
# One entry below uses it - 2a04:2a00::/32, our own infrastructure block - and the test is not "we
# operate it" but "nobody else can get space inside it". That distinction is exactly the one the
# removal recorded at the bottom of this file turns on: 2a04:2a01::/32 is also ours and was taken OUT,
# because it is the agent egress block and our own customers' agents live inside it, which makes it
# occupiable by anyone who signs up. Operated-by-us is not the test. Un-occupiable is.
#
# PROVENANCE, and why this file is data rather than constants in the builder: every line is checkable, a new
# entry is a one-line reviewable diff, and the reason travels with the address.
#
# Format:  <address-or-prefix>   <source>   <what it is>

# ---- Our OWN infrastructure, because a self-pinning outage was reachable ----
#
# ns1 and ns2 sit in commercial VPS space, which is the most heavily SBL-listed category of address
# space there is. A listing on a prefix covering ns2, plus an rpz-nsip trigger, would have made every
# slaving resolver NXDOMAIN our own nameserver and everything served from it - including the zone
# carrying the policy. The resolver could then no longer refresh, so it would be PINNED on the bad
# policy until the SOA expire, and recovery would require resolving the very names the bad zone
# forbids. There is no remote remedy for that; every operator would have to delete the zone by hand.
# It would also have taken out the builder's own graph endpoint.
#
# Holding our own space harmless is not self-dealing: it is the difference between a bad build being
# recoverable and being terminal.
#
# HOST ADDRESSES, NOT THE PREFIXES AROUND THEM. ns1 and ns2 are rented from a commercial cloud, so
# the /24 and /48 that CONTAIN them are rentable by anyone with a credit card. Exempting those would
# publish an occupiable bypass of this feed, with instructions, which is exactly the test the top of
# this file sets out and exactly the ground on which the agent egress prefix was removed below. The
# narrowest thing that closes the self-pinning hole is the single address each service answers on.
#
# This is therefore a MAINTENANCE POINT: if a node is rebuilt on a new address, the entry has to move
# with it, or the hole reopens quietly. Nothing verifies the ADDRESSES automatically, because doing so
# would mean a DNS lookup inside a build; what IS enforced is the SHAPE, which is the part that went
# wrong: a test refuses any entry in this section that is not a single host (/32 or /128), so the
# covering cloud prefix cannot come back.
